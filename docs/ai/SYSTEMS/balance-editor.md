# Система: Balance Lab

> Обновлено: 2026-04-05.

## Что это
`tools/balance-editor.html` остаётся standalone repo-local host без build step, но с 2026-04-03 это уже не только analytics tab. Поверх существующего editor shell загружается `tools/balance-lab.js`, который использует общий вычислительный слой из `tools/balance-shared.js`, registry/lock layer из `tools/balance-registry.js` и bounded optimizer из `tools/balance-optimizer.js`.

Итоговая surface решает четыре задачи сразу:
- редактирует рабочие JSON-копии в памяти;
- синхронизирует browser analytics и CLI через общий kernel;
- оценивает surrogate matrix по level bands / profiles / goals;
- готовит safe write-back только для allowlisted JSON и runtime-констант из `game.js`, не трогая locked world-events surfaces.

С 2026-04-05 Goals panel больше не ограничивается expert-table. Поверх таблицы целей появился high-level goal profile: три slider-поля (`desiredTtk`, `zombiePressure`, `progressionPressure`) и preset-кнопки живут в shared-kernel и browser shell, но становятся canonical goals только после явного Apply. Это позволяет быстро попросить «длинный TTK, но всё ещё опасных зомби», не переписывая вручную все диапазоны целей: [tools/balance-shared.js](../../../tools/balance-shared.js#L26-L201), [tools/balance-shared.js](../../../tools/balance-shared.js#L597-L663), [tools/balance-lab.js](../../../tools/balance-lab.js#L288-L362), [tools/balance-lab.js](../../../tools/balance-lab.js#L662-L696).

Optimizer path теперь отдельно защищён от catastrophic outlier cases на верхней границе диапазона. Matrix score в `evaluateRange()` сравнивает не только линейное отклонение, но и log-ratio gap, а candidate search больше не крутится только вокруг маленьких локальных шагов: он обязан проверять min/max и half-step к экстремумам, чтобы ручной взрыв вроде `tank_lvl60.stats.baseDamage = 61000000000` или `types[59].Health = 2627515200359` действительно становился видимым и оптимизируемым: [tools/balance-shared.js](../../../tools/balance-shared.js#L685-L719), [tools/balance-optimizer.js](../../../tools/balance-optimizer.js#L37-L72), [tools/balance-registry.js](../../../tools/balance-registry.js#L173-L229), [Test/pack8/balanceOptimizerLocks.test.js](../../../Test/pack8/balanceOptimizerLocks.test.js#L263-L311).

Дополнительно host shell теперь version-bust'ит Balance Lab runtime scripts, а Optimize panel обязан явно показывать состояние `0 enabled tunables`: при нуле чекбоксов optimize-run не должен выглядеть как сломанная кнопка, он должен быть disabled и сопровождаться объясняющим текстом. Browser overlay при `lang="ru"` теперь обязан рендерить root tabs, optimize metrics и tunables table на русском, а не оставлять старые английские display-labels из overlay-слоя.

Absolute tunables в optimizer больше не читаются из устаревшего snapshot tunable-state: baseline и candidate search обязаны стартовать от текущей working copy editor'а, даже если пользователь уже руками изменил JSON/runtime-поле до запуска Optimize. User-edited `directionBias` из Tunables table тоже считается каноническим входом optimizer'а, а explainability больше не завязана на старые английские group names registry и остаётся специфичной для русских групп.

Manual-profile surrogate для каждого level band теперь по умолчанию якорится на верхнюю границу диапазона, а не на mid-level band. Это важно для edge-case вроде level 60: экстремальный перекос на потолке band должен сразу поднимать matrix score и становиться видимым для optimizer, а не оставаться невидимым из-за midpoint-only seed. Default goals для manual-profile больше не нормализуются от текущего manual-scenario state; вместо этого они берут band-reference из `base/average/peak`, чтобы уже сломанные assets на верхней границе band не считались «нормой» при первой загрузке инструмента.

## Инварианты ⚠️
- Tool остаётся standalone surface и ожидает запуск через корень репозитория или static server с тем же относительным путём. Browser host работает с `../assets/*`, а Balance Lab дополнительно читает runtime sources `../game.js`, `../src/config/worldEvents.js` и `../src/systems/worldEventsRuntime.js`: [tools/balance-editor.html](../../../tools/balance-editor.html#L283), [tools/balance-lab.js](../../../tools/balance-lab.js#L621).
- Browser host должен version-bust'ить подключаемые `balance-shared.js`, `balance-registry.js`, `balance-optimizer.js` и `balance-lab.js`, если задача меняет их wiring/UX в одном релизе. Иначе reload может оставить новую HTML-обвязку поверх старого cached runtime: [tools/balance-editor.html](../../../tools/balance-editor.html#L262).
- `window.BalanceEditorApp` и событие `balance-editor:state-changed` являются каноническим seam между host и Balance Lab. Новые browser-side расширения не должны обращаться к внутренним локальным переменным editor'а в обход этого API: [tools/balance-editor.html](../../../tools/balance-editor.html#L317), [tools/balance-lab.js](../../../tools/balance-lab.js#L621).
- Общие формулы теперь живут в `tools/balance-shared.js`; browser analytics и CLI sim обязаны использовать один и тот же kernel для tank DPS/shot damage, zombie HP, fence survival, drone contribution, progression pressure и matrix evaluation. Если меняется runtime-formula, сначала обновляй shared kernel, а уже потом editor/CLI shells: [tools/balance-shared.js](../../../tools/balance-shared.js#L525), [tools/balance-shared.js](../../../tools/balance-shared.js#L667), [tools/balance-sim.js](../../../tools/balance-sim.js#L209).
- Registry является allowlist-слоем, а не произвольным patch-engine. Write-path допускает только JSON-конфиги и ограниченный набор runtime-констант из `game.js`; locked surfaces из [src/config/worldEvents.js](../../../src/config/worldEvents.js) и [src/systems/worldEventsRuntime.js](../../../src/systems/worldEventsRuntime.js) видимы в UI, но никогда не должны попадать в optimizer result или direct write-back: [tools/balance-registry.js](../../../tools/balance-registry.js#L464), [tools/balance-registry.js](../../../tools/balance-registry.js#L483), [tools/balance-registry.js](../../../tools/balance-registry.js#L531).
- Optimize-run меняет только checkbox-enabled tunables и только по выбранным scenarios. Unchecked параметры должны оставаться нетронутыми, reset обязан возвращать состояние к pre-optimize snapshot, а при `0` enabled tunables Optimize panel должен блокировать запуск и давать явное объяснение вместо silent no-op. Для absolute tunables baseline и candidate search обязаны брать текущее значение из working copy, а не из stale init-snapshot; user-edited `directionBias` из Tunables table должен реально влиять на candidate set optimizer'а.
- High-level goal sliders сами по себе не меняют expert-table, optimizer и write-preview. До явного `Применить к таблице целей` они меняют только `labState.goalTuning` и help-summary; после применения таблица целей перестраивается, предыдущий optimizer result сбрасывается, а Write panel теперь обязан явно объяснять, что goals не пишутся в игру напрямую и сперва должны пройти через optimizer: [tools/balance-lab.js](../../../tools/balance-lab.js#L245-L252), [tools/balance-lab.js](../../../tools/balance-lab.js#L288-L362), [tools/balance-lab.js](../../../tools/balance-lab.js#L435-L487), [tools/balance-lab.js](../../../tools/balance-lab.js#L662-L685).
- `collectWriteEntries()` и write panel работают только через diff-preview и явный allowlisted file map. Direct write разрешён только после явного выбора корня репозитория пользователем через File System Access API; если API недоступен, tool должен оставаться в export-only режиме (`manifest`/`patch`), а не пытаться писать скрытно: [tools/balance-lab.js](../../../tools/balance-lab.js#L354).

## Ограничения
- Это repo-local balance workbench, а не gameplay runtime. Изменения здесь не подключаются через `index.html` и не должны описываться как Canvas hot path или Phaser scene logic.
- Optimizer здесь эвристический и bounded. Он помогает найти безопасный candidate set, но не гарантирует глобально оптимальное решение и не заменяет gameplay judgement.
- Goal sliders/presets не являются отдельной write-surface: наружу по-прежнему уходят только явные diff'ы целей, tunables и allowlisted runtime/JSON patch entries. Сам `goalTuning` — browser-state для синтеза goals, а не новый persisted config.
- Direct write-back зависит от браузерной поддержки File System Access API. На неподдерживаемых хостах канонический fallback — manifest/patch export, а не частичный silent write.
